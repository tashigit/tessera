Vertex consensus for ROS 2: concepts and protocol design

This volume builds the mental model and the design skill: what the Tashi Vertex engine actually guarantees, how leaderless fleet coordination falls out of one ordered log, and how to design a correct application protocol before writing code. I use tessera's four-robot route-exploration simulation as the worked example. For implementation you then build on the vertex_fleet library, which is Volume 2; this volume shows the library's concepts and, where useful, what it does underneath.

The series. 1 · Concepts and protocol design (you are here)  →  2 · The fleet API (build your integration)  →  3 · Crate-level internals (non-ROS embeddings and adapters). In a hurry? Start with Volume 2 and return here when you design your own protocol.

You need: ROS 2 Jazzy (or the tessera Docker harness), Rust, and access to the tessera and tashi-vertex-rs repositories.

The mental model: one ordered log, everywhere

Tessera ships vertex_node, a ROS 2 node that wraps the Tashi Vertex engine (a hashgraph-family aBFT protocol: gossip about gossip plus virtual voting). You run one vertex_node per agent. Each binds a UDP socket and gossips peer to peer with the others.

The contract is small and it is the whole point:

  • You publish opaque bytes to /vertex/tx. Vertex neither inspects nor interprets them.
  • Every peer receives the same finalized sequence of events on /vertex/event, byte for byte, in the same order.

That is the entire integration surface. Your application never talks agent to agent. Each agent submits proposals into the log and folds the log into local state. Because every agent folds the same log with the same pure function, every agent derives the same state, and coordination falls out for free.

InterfaceTypeDirectionMeaning
/vertex/txVertexTransactionyou → enginesubmit opaque payload bytes
/vertex/eventVertexEventengine → youfinalized events in consensus order: hash, transactions[], consensus_at, created_at
/vertex/transitionVertexTransition srvyou → enginelifecycle: configure / activate / deactivate / cleanup / shutdown
/vertex/statusVertexStatus srvyou → enginesnapshot: running, peer count, tx and event counters, last error
/vertex/lifecycle/statetopicengine → youcurrent lifecycle state

  3. Claim on node 2, then Crash it. Click Timeout dead route on a survivor: the route frees everywhere. Revive node 2 and note its log froze while it was down. Rejoining a running session is a separate upstream feature, which is why the real robots stay active across decisions they must act on.

Design before code: what goes through consensus

The one decision that shapes the whole integration: split your system into agreements and reflexes.

  • Agreements go through Vertex. Anything two or more agents must see identically: task assignment, shared world knowledge, mission phase, restarts. In the example: who explores which route, which routes are blocked, which route won.
  • Reflexes stay local. One agent's sensors, motion control, and safety behavior. In the example: waypoint following, stall detection, and bot-to-bot collision avoidance all run locally. A safety reflex cannot wait for a consensus round trip.

Local facts still become shared truth, but only by being submitted and finalized. An agent detects "my route is blocked" with its own sensors, then publishes a blocked record. The fact exists for the fleet only once it appears in the log.

Then size the fleet. Vertex is BFT with the standard quorum, so pick n for the faults you must survive:

Peers nFaults tolerated f = ⌊(n−1)/3⌋Notes
30fine for development, no fault tolerance
41smallest fleet that survives one crashed agent
72

Step 1Set up the workspace

Check out tessera and tashi-vertex-rs side by side. The Rust crate is a path dependency of tessera's vertex_core, so the sibling layout is required.

shell
mkdir consensus-fleet && cd consensus-fleet
git clone git@github.com:tashigit/tessera.git
git clone git@github.com:tashigit/tashi-vertex-rs.git

The fastest path to a working build is tessera's Docker harness. It gives you ROS 2 Jazzy, the ros2-rust toolchain, and cached colcon builds without touching your host:

shell
cd tessera
docker compose build            # build the Jazzy environment image (once)
docker compose run --rm build   # colcon build vertex_ros2 inside the container
docker compose run --rm shell   # interactive shell with the env sourced

On a native ROS 2 Jazzy install, build with colcon from a workspace that contains both checkouts under src/:

shell
colcon build --packages-up-to vertex_ros2 --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash
On Linux the colcon-installed vertex_node has no rpath to libtashi-vertex.so. Find the library under your build tree and add its directory to LD_LIBRARY_PATH before launching. The harness does this in docker/entrypoint.sh (export_tv_libpath), which is worth copying.

Step 3Launch the mesh

One vertex_node per agent, each configured with its own key and bind address plus everyone else's pubkey@addr. The contract topics are absolute (/vertex/*), so when several nodes share a machine or a ROS graph, remap them into per-agent namespaces. This launch pattern comes straight from the example and scales to any n:

python — fleet.launch.py
import json
from launch import LaunchDescription
from launch_ros.actions import Node

peers = json.load(open("peers.json"))

def generate_launch_description():
    actions = []
    for i, me in enumerate(peers):
        ns = f"/agent_{i}"
        others = [p for j, p in enumerate(peers) if j != i]
        actions.append(Node(
            package="vertex_ros2", executable="vertex_node", name=f"vertex{i}",
            remappings=[(f"/vertex/{t}", f"{ns}/vertex/{t}")
                        for t in ("tx", "event", "sync_point", "status", "transition")]
                      + [("/vertex/lifecycle/state", f"{ns}/vertex/lifecycle/state")],
            parameters=[{
                "vertex.bind_address": me["addr"],
                "vertex.secret_key_base58": me["secret"],
                "vertex.peers": [f"{p['public']}@{p['addr']}" for p in others],
                "options.heartbeat_us": 50000,
            }],
        ))
        # + your application node in the same namespace (step 7)
    return LaunchDescription(actions)

The parameters you will actually touch:

ParameterPurpose
vertex.bind_addressliteral IP:port to bind, no DNS
vertex.secret_key_path / vertex.secret_key_base58this node's identity (file form recommended)
vertex.peersstring array of <base58_pubkey>@<ip:port> for every other peer
options.heartbeat_usengine heartbeat; 50000 works well for tests
vertex.joining_running_sessionrejoin an in-flight session (upstream feature, off by default)
bridge.tx_channel_capacity / bridge.event_channel_capacityROS↔engine buffer bounds; overflow shows in tx_rejected_total

Step 4Bring the nodes to Active

vertex_node starts unconfigured and publishes nothing until it is driven through its lifecycle. Nothing appears on /vertex/event while a node is Inactive, which is itself part of the contract and is what the lifecycle tests assert. From a shell:

shell
ros2 service call /agent_0/vertex/transition vertex_ros2_msgs/srv/VertexTransition "{transition: configure}"
ros2 service call /agent_0/vertex/transition vertex_ros2_msgs/srv/VertexTransition "{transition: activate}"

In a real deployment you do not do this by hand: a vertex_fleet.VertexAgent (Volume 2) drives its own engine through configure and activate, retrying until the transition service is up and both verbs succeed, and holds your periodic logic back until the engine is Active. The shell commands above are what that bring-up does underneath, and they remain the right tool for poking a mesh interactively.

Sanity check the mesh with ros2 service call /agent_0/vertex/status vertex_ros2_msgs/srv/VertexStatus: it reports running, peer_count, and submit/reject counters.

Step 5Define the payload protocol

Vertex moves opaque bytes, so the record format is entirely yours. Small JSON records work well and stay debuggable. The example's protocol is four route-exploration verbs plus three housekeeping ones, and its shape transfers to almost any task-allocation problem:

jsonc — one record per transaction
{ "op": "claim",   "bot": 2, "route": "R1", "epoch": 0 }  // propose to take a task
{ "op": "blocked", "bot": 2, "route": "R1", "epoch": 0 }  // my sensors say: task impossible
{ "op": "arrived", "bot": 1, "route": "R2", "epoch": 0 }  // task proven done
{ "op": "timeout", "bot": 3, "victim": 2, "route": "R3", "epoch": 0 }  // lease expiry
{ "op": "unblock_all", "bot": 3, "seq": 2, "epoch": 0 }   // world changed, shared facts stale
{ "op": "reset", "epoch": 1 }                            // wipe and restart the mission

Four rules make a protocol like this correct under concurrency. They are the accumulated lessons of the example, so I recommend adopting all of them:

  1. First in the log wins. Never negotiate. When two agents claim the same task, the finalized order is the arbiter: the first claim is valid, the second is a no-op. Every conflict resolves this way, on every agent identically, with no extra messages.
  2. Every record is idempotent or a checked no-op. Multiple agents will propose the same thing concurrently (several survivors propose the same timeout, four coordinators relay the same reset). Applying a duplicate must change nothing.
  3. Carry an epoch. Stamp every record with the current epoch and ignore records from older epochs. A reset bumps the epoch. This makes restarts a single consensus point instead of a distributed cleanup problem.
  4. Lease anything an agent can hold. A crashed agent cannot release what it holds. Let any agent propose a timeout for an assignment that has produced no outcome within a lease window sized above the worst-case task time. The release restores progress; exclusivity was never at risk because the dead agent held the task alone.
Rules 1 and 2 are yours to design into the records. Rule 3's mechanics (epoch stamping on every proposal, epoch gating on every fold, reset handling) ship in vertex_fleet, so in Volume 2 you inherit them rather than implement them.

Step 6The replicated state machine

This is the heart of the integration and it should be the most boring code you write: a pure fold from ordered records to state. No ROS imports, no I/O, no clocks, no randomness. Purity is what makes "same log in, same state out" testable on your laptop.

You write it by subclassing vertex_fleet.ReplicatedState: the base owns epoch gating, reset handling, and the canonical record encoding, and your subclass folds only its own ops. This is the route-exploration protocol from §3, condensed (the shipped version is mission_fsm.py in the repository):

python — fleet_state.py (pure, condensed from the simulation)
from vertex_fleet import ReplicatedState

class FleetState(ReplicatedState):
    def __init__(self, tasks, num_agents):
        self.tasks, self.n = list(tasks), num_agents
        super().__init__()          # sets epoch = 0 and calls wipe()

    def wipe(self):                 # construction and consensus `reset`
        self.assigned, self.blocked, self.arrived = {}, set(), set()
        self.winner = None

    def apply_record(self, rec):    # one same-epoch record, log order
        op, bot, task = rec["op"], rec.get("bot"), rec.get("route")
        if op == "claim":           # first claim in the log wins
            if (bot not in self.assigned and bot not in self.arrived
                    and task in self.tasks
                    and task not in self.assigned.values()
                    and (task not in self.blocked or rec.get("retry"))):
                self.assigned[bot] = task
        elif op == "blocked":
            self.blocked.add(task)
            if task == self.winner: self.winner = None
            self.assigned = {b: t for b, t in self.assigned.items()
                             if b != bot and t != task}
        elif op == "arrived":
            self.arrived.add(bot); self.blocked.discard(task)
            if self.winner is None:
                self.winner = task; self.assigned.clear()
            self.assigned.pop(bot, None)
        elif op == "timeout":       # lease: no-op unless still held
            if self.assigned.get(rec.get("victim")) == task:
                del self.assigned[rec["victim"]]

    def role(self, me):             # what should THIS agent do now
        if me in self.arrived: return ("done", None)
        if me in self.assigned: return ("work", self.assigned[me])
        if self.winner: return ("converge", self.winner)
        return ("wait", None)
The one structural rule: this state must have a single mutation path, the consensus event callback. If any other input can change it, agents can diverge and the whole guarantee is gone. Sensors, timers, and services may read it and may propose records, never write it. VertexAgent enforces this by construction; keep it true in anything you add.

Step 7Wire the application node

The application node connects three things: the log (folded into state for you), your intent (proposals), and your actuators (act on the derived role). On vertex_fleet.VertexAgent that wiring is inherited: the event subscription, the epoch-stamped transaction publisher, the lifecycle bring-up, and the tick timer all come from the base, and what remains is exactly your application. The shipped mission_coordinator is this skeleton grown up:

python — fleet_agent.py
from vertex_fleet import VertexAgent, spin_agent
from fleet_state import FleetState

class FleetAgent(VertexAgent):
    def __init__(self):
        super().__init__("fleet_agent",
                         FleetState(tasks=["R1", "R2", "R3", "R4"],
                                    num_agents=4))
        self.me = self.declare_parameter("agent_id", 0).value

    def tick(self):                # local intent + local sensing -> proposals;
                                   # runs only while the engine is Active
        role, task = self.state.role(self.me)
        if role == "wait" and (free := self.pick_free_task()):
            self.propose({"op": "claim", "bot": self.me, "route": free})
        if role == "work" and self.task_done(task):
            self.propose({"op": "arrived", "bot": self.me, "route": task})

    def on_state_changed(self):    # derived role -> actuators, no negotiation
        role, task = self.state.role(self.me)
        self.drive_toward(task) if role in ("work", "converge") else self.hold()

def main():
    spin_agent(FleetAgent)

Underneath, the base does what you would otherwise write by hand: a reliable subscription to vertex/event whose callback is the single place self.state mutates, a publisher on vertex/tx that stamps every proposal with the current epoch, and the configure-then-activate loop from step 4. Volume 2 walks this assembly line by line; the raw wiring is in vertex_fleet/vertex_fleet/agent.py if you want to read it.

Notice what tick does not do: it never assumes its own claim succeeded. It proposes and keeps waiting. The agent starts working only when its claim comes back through the consensus fold and role() says so. Here is that rule in a real trace from the example's consensus logs. The robot submits its claim, keeps waiting, and switches to explore only after the claim returns finalized, sequenced behind three other claims it also learned about:

Step 8Test at three layers

Unit: determinism of the fold

Feed the same record log to N independent instances of your state machine and assert they agree. Plain Python, no ROS, runs anywhere (the ReplicatedState layer imports without ROS for exactly this reason). This is where protocol bugs die cheapest, and vertex_fleet/test/test_state.py in the repository is the template:

python — test_fleet_state.py
def test_exclusive_assignment_and_agreement():
    fleet = [FleetState(["R1", "R2", "R3", "R4"], 4) for _ in range(4)]
    log = [{"op": "claim", "bot": 0, "route": "R1", "epoch": 0},
           {"op": "claim", "bot": 1, "route": "R1", "epoch": 0}]   # conflict!
    for f in fleet:
        for rec in log: f.apply(rec)
    assert all(f.assigned == {0: "R1"} for f in fleet)   # one winner, everywhere

Integration: real consensus, mock bodies

Use launch_testing to start real vertex_node peers, your application nodes, and a mock in place of the physical layer (the example's mock_robot.py is 100 lines: it turns drive commands into pose updates). Assert the outcomes, not the timing: everyone finishes, everyone agrees, no task was ever held twice. Then add the assertion that catches everything else, byte-identical event streams:

python — inside the launch_test
# collect (hash, payloads) per node from /agent_i/vertex/event, then:
min_len = min(len(events[i]) for i in range(n))
for idx in range(min_len):
    for i in range(1, n):
        assert events[0][idx] == events[i][idx]   # the total-order guarantee

Adversarial: kill things

The example ships three tests worth copying wholesale, each about 200 lines:

  • Fault injection (fault_injection.launch_test.py): make the victim's task the only viable one, SIGKILL its engine, coordinator, and mock mid-task, and assert the survivors lease-timeout the task, re-claim it, and finish with byte-identical streams. With n=4 this proves f=1 for real.
  • Lifecycle churn (lifecycle_churn.launch_test.py): deactivate one engine mid-mission, force traffic, assert zero publishes on its /vertex/event while Inactive, reactivate, and finish.
  • Soak (soak_missions.launch_test.py): randomized back-to-back missions restarted through reset epochs, asserting every mission terminates consistently and engine RSS stays bounded.

Wire the fast ones into CI on every push and keep the soak nightly. The example's sim-test job in .github/workflows/ci.yml is a working template.

Pitfalls I hit so you don't have to

  • Acting before finalization. If an agent starts working the moment it publishes a claim, two agents can work the same task until the log catches up. Propose, then wait for your own record to come back.
  • Letting physical facts lie. My arrival check originally tested only "past the goal line". A world change shoved a robot down a different lane and it credited its assigned route with a phantom arrival, poisoning the shared state. Gate every self-reported fact on evidence it is the fact you claim (in the example: also on the claimed route's row).
  • Routing reflexes through the log. Collision avoidance through consensus adds a round trip you cannot afford at reflex speed. Keep safety local and deterministic. In the example the bots exchange poses on a sim-local radio and break ties by agent id.
  • Flooding side channels. High-rate sensor streams sharing a transport with your command path will starve it. My pose feed once delayed drive commands by minutes. Throttle telemetry, and keep the consensus path on its own dedicated topics.
  • Assuming a restarted node catches up. Vertex orders what a node observes while participating. A node that was down during decisions does not relearn them on rejoin unless you build state transfer (upstream: vertex.joining_running_session). Design so restarted agents either do not need missed events or get reset into a fresh epoch.
  • Non-determinism creeping into the fold. A single random(), clock read, or dict-iteration dependence inside apply() and your agents silently diverge. Keep randomness in the proposal side (which task to try claiming), never in the fold.
