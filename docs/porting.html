Porting a broker-based fleet to Vertex consensus

Many multi-robot systems already coordinate through a message broker: MQTT topics for shared state, plus a hand-rolled voting protocol for anything that needs agreement. This volume ports one, end to end. The result ships in the repository as the second simulation: five Pioneer 3-AT robots sweeping an outdoor arena, with every shared decision derived from the ordered log.

The series. 1 · Concepts and protocol design  →  2 · The fleet API  →  3 · Crate-level internals  →  4 · Porting (you are here). Read Volume 2 first: this volume assumes the two base classes and shows how an existing design maps onto them.

You need: the tessera workspace built (Volume 2, step 1), Docker for the headless run, and optionally Webots R2025a for the live world.

Where this fits

Volumes 1 to 3 build protocols from scratch. This one starts from a working system with a different transport and asks the porting question: which parts move, which parts stay, and which parts simply disappear. The answer is the same for most broker-based fleets, so the worked example doubles as a template.

Everything here runs against real consensus in CI. The code lives in its own directory, vertex_ros2/test/simulation_arena/: the fold in nodes/arena_fsm.py, the agent in nodes/arena_coordinator.py, the world in worlds/pioneer_arena.wbt, and the design document in its README.md. The route-exploration scenario from Volumes 1 to 3 sits beside it in vertex_ros2/test/simulation/.

The system being ported

The source system is a classic MQTT-coordinated exploration stack. Five Pioneer 3-AT robots explore an arena of trees, rocks, pits, and the occasional deer. Each robot runs a local autonomy loop (mapping, goal selection, path following), and everything cross-robot rides a four-broker MQTT cluster:

  • frontier and path sharing on coordination/# topics,
  • mission status and territory on robots/robot_i/# topics,
  • and a telemetry-health voting protocol: every robot publishes sensor-stream snapshots, initiates votes on them, tallies YES/NO responses from its peers against a 4-of-5 threshold, and gates object detections on the outcome, so a robot with a dead camera cannot poison the shared picture.

Two details matter for the port. First, the voting protocol exists because a broker offers pub/sub but no agreement primitive, so agreement had to be built on top, with request IDs, tallies, partial-consensus timers, and TTLs. Second, that protocol only works because the broker delivers messages to every subscriber in the same order. The predecessor's own documentation says so explicitly: it relies on the transport's total ordering for state machine replication. The ordering engine under that broker is the same Tashi consensus this integration exposes directly. The port removes the middleman.

The porting method

One sorting rule drives the whole port. For every piece of data the broker carried, ask: must the fleet agree on it, or does each robot only need to hear about it?

Broker system

  • 4-broker MQTT cluster, credentials, bridge node per robot
  • vote/tally protocol: request IDs, thresholds, partial-consensus timers, TTLs
  • per-robot bridge tables mapping ROS topics to MQTT topics and back
  • ordering an implicit property of the transport

Consensus port

  • one vertex_node per robot, peered over UDP, no server
  • agreement is the transport: one ReplicatedState fold
  • one agent class proposing records, one fold consuming them
  • ordering explicit, byte-identical, and asserted in CI

Three destinations for every broker topic:

  1. Stays robot-local. High-rate sensor and control data that no other robot needs verbatim: lidar scans, camera frames, wheel commands. These never touch consensus. They stay ordinary ROS topics inside the robot's namespace.
  2. Becomes a record. Anything that changes shared state: task claims, task outcomes, health, sightings. These become small JSON records proposed into the log and folded by everyone.
  3. Disappears. Every mechanism that existed to approximate agreement over pub/sub: the vote messages, the tallies, the request TTLs, the result broadcasts. The ordered log makes them redundant.
The predecessor also carried each robot's occupancy grid and full planned paths through the broker. That is category 1 thinking trapped in a category 2 transport: peers consumed them as advisory context, never as agreed state. The port replaces the grid-and-frontier machinery with a fixed sector grid so that the shared thing (who sweeps where) is a claim, which is category 2, and everything else stays local. When you port your own system, expect to re-draw this line rather than copy topics one for one.

Step 2Design the records

Seven operations cover the scenario. All carry epoch, and reset comes free with the base class:

jsonc
{ "op": "claim",       "bot": 2, "sector": "S07", "epoch": 0 }
{ "op": "explored",    "bot": 2, "sector": "S07", "epoch": 0 }
{ "op": "abandon",     "bot": 2, "sector": "S07", "epoch": 0 }
{ "op": "unreachable", "bot": 2, "sector": "S07", "epoch": 0 }
{ "op": "health",      "bot": 2, "seq": 41, "ok": true, "epoch": 0 }
{ "op": "suspect",     "bot": 3, "victim": 2, "seen_seq": 41, "epoch": 0 }
{ "op": "detection",   "bot": 1, "seq": 0, "label": "deer", "x": -14.6, "y": 9.6, "epoch": 0 }

The design moves worth stealing:

  • The health beacon is self-assessed and sequenced. Each robot checks its own sensor-stream freshness locally (lidar age, camera age) and folds the verdict as a beacon with a monotonic seq. The fold ignores stale or duplicate sequences, so redelivery and reordering of proposals by the network cannot corrupt anything.
  • Silence needs a second mechanism. A crashed robot never sends its own not-ok beacon. So any live robot may propose suspect, carrying the victim's last folded seq. The fold acts only if no newer beacon landed first. That one condition makes late beacons void stale suspicions, makes duplicates no-ops, and lets every robot propose concurrently without coordination. It is the same shape as the route scenario's lease timeout in Volume 1.
  • Gating is a fold rule, not a check at the sender. A detection is accepted only if its reporter is healthy at that point in the log. Every robot applies the rule to the same ordered stream, so every robot keeps the identical detection list. The predecessor needed a full voting round to make this call.

Step 3Write the fold

The whole shared state is one ReplicatedState subclass, pure and unit-testable on any host with no ROS. The claim rule shows the flavor:

python · nodes/arena_fsm.py
def apply_record(self, rec):
    op = rec["op"]
    bot, sector = rec.get("bot"), rec.get("sector")
    if op == "claim":
        ok = (self.phase == EXPLORING and bot is not None
              and bot not in self.unhealthy
              and sector in self.sectors
              and sector not in self.explored
              and sector not in self.unreachable
              and sector not in self.claimed
              and bot not in self.claimed.values())
        if ok:
            self.claimed[sector] = bot
    elif op == "explored":
        # only the claim holder can credit a sector: a bot whose claim
        # was released must re-claim before reporting
        if self.claimed.get(sector) == bot:
            self.explored.add(sector)
            del self.claimed[sector]

Exclusivity is not enforced anywhere else. There is no lock service and no arbiter node. Two robots may race a claim, and the one whose record lands first in consensus order wins, on every robot, including the loser. The loser's agent sees the fold say so and claims a different sector.

Compare the health machinery line for line with the predecessor:

Before: vote and tally

  • initiator publishes a snapshot + request ID every 5 s
  • each peer validates freshness, votes YES/NO
  • initiator tallies against 4-of-5, runs a 3 s partial-consensus timer
  • result broadcast back through the broker
  • requests expire on a 20 s TTL

After: fold

  • each robot folds a sequenced health beacon
  • not-ok marks it unhealthy and releases its claim, ok readmits it
  • suspect covers silent crashes
  • verdicts identical everywhere by construction, nothing to broadcast

Step 4Write the agent

The agent is a VertexAgent subclass with the standard split: tick() senses and proposes, the fold mutates, on_state_changed() reacts. Porting adds three loops the predecessor ran as separate nodes:

python · nodes/arena_coordinator.py (tick, abridged)
def tick(self):
    # 1. the health beacon: the predecessor's telemetry_monitor_node,
    #    reduced to one sequenced self-assessment
    if beacon_due:
        self._health_seq += 1
        self._emit({"op": "health", "bot": self.my_id,
                    "seq": self._health_seq, "ok": self._self_ok()})

    # 2. the silence lease: suspect a peer whose beacons stopped
    for b in silent_peers:
        self._emit({"op": "suspect", "bot": self.my_id, "victim": b,
                    "seen_seq": self.state.health_seq.get(b, -1)})

    # 3. physical outcomes for my claimed sector, then the claim loop
    if covered:  self._emit({"op": "explored", ...})
    elif stalled: self._emit({"op": "abandon" or "unreachable", ...})
    if idle_and_healthy and claim_due:
        self._emit({"op": "claim", "bot": self.my_id,
                    "sector": nearest_free_sector})

Note what the agent never does: it never marks anyone unhealthy, never grants itself a sector, never decides a detection is trusted. It only proposes. Every verdict comes back out of the fold, or it does not happen. That discipline is what the library's single-mutation-path rule buys you, and it is the structural difference from the predecessor, where each node kept its own active_requests bookkeeping and trusted it.

Step 5Reconnect the body

The predecessor's Webots controllers exchanged sensor data with ROS through polled files in /tmp. That cannot cross the container boundary in the tessera split (native Webots on the host, the ROS and Vertex graph in Docker), and it was always a latency tax. The port keeps only the Webots assets: the arena world and the five Pioneer 3-AT robots with their Sick LMS 291 lidars and webcams. Each robot gains a GPS and an inertial unit, and a new controller (controllers/pioneer_explorer/) bridges over rosbridge's WebSocket exactly like the route scenario's follower:

NodeWherePubSub
pioneer_explorerMac (Webots)/robot_i/pose, /robot_i/telemetry/robot_i/goto
arena_coordinatorcontainer/robot_i/vertex/tx, /robot_i/goto, /robot_i/mission_state/robot_i/vertex/event, /robot_i/pose, /robot_i/telemetry, /robot_i/detection
vertex_nodecontainer/robot_i/vertex/event/robot_i/vertex/tx

The telemetry topic carries per-stream sensor ages. The agent turns them into its health beacon, which is the live path from a dying camera to a fleet-wide, agreed, reversible verdict. Headless, nodes/mock_pioneer.py stands in for Webots with straight-line kinematics, a scripted sensor outage, and planted detections, so CI asserts the whole loop against real consensus with no simulator.

The fold itself has fifteen pure-python unit tests covering the exclusivity rules, holder-only reporting, stale beacon sequences, suspicion races, detection gating, and epoch resets.

Pitfalls

  • Do not port the vote. The strongest temptation is transliterating the old protocol, request IDs and all, onto the log. Ask instead what state the vote was computing, then fold that state directly. The entire vote/tally subsystem here compressed into the health and suspect rules.
  • Keep clocks out of the fold. The predecessor's freshness checks compared wall clocks, which is fine at a proposal site and fatal inside a fold (robots would diverge). Every time-like decision here folds through data: beacon sequences, and suspicions that carry the observed sequence.
  • Only the holder reports. An explored from a robot whose claim was released mid-sweep (a health blip) must not credit the sector, or coverage could be claimed off stale work. The fold checks the claim, not the reporter's sincerity.
  • Never trust your own proposal. The agent that proposes a claim does not own the sector until the claim comes back finalized. This falls out of the library, but broker-era code is full of local bookkeeping that assumes its own messages succeeded. Delete it.
  • Category 1 data will try to sneak in. Resist folding paths, grids, or camera frames. If nobody must agree on it, it does not belong in the log.
