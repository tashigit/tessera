Wiring Tashi Vertex into a new project at the crate level

Volumes 1 and 2 treat tessera's vertex_node as a black box behind ROS topics. This one opens the box: how the crates fit together, how to embed the engine in a plain Rust process with no ROS at all, and how to write your own middleware adapter the way vertex_ros2 was written. Everything here comes from tessera's vertex_core crate and its real tests.

The series. 1 · Concepts and protocol design  →  2 · The fleet API (the default path for ROS 2 projects)  →  3 · Crate-level internals (you are here). Come here when your process cannot be a ROS 2 node, or you are building an adapter.

You need: Rust (stable), CMake, and access to the tessera repository. No ROS required until section 5.

Anatomy of vertex_core

vertex_core is a plain cargo crate with no ROS dependency. It owns everything that must be correct: the lifecycle state machine, the engine thread, the bounded channels, and the conversion out of FFI memory. The API you program against is small:

rust — the surface
use vertex_core::{Controller, Config, PeerConfig, BridgeConfig, VertexOptions};
use vertex_core::{EventRecord, LifecycleState, StatusSnapshot};

let mut c = Controller::new();          // state: Unconfigured
c.configure(config)?;                     // -> Inactive (validates, no I/O)
let (event_rx, sync_rx) = c.activate()?; // -> Active (spawns the engine thread,
                                          //    binds UDP, starts the engine)
c.submit(payload);                        // bytes -> consensus (non-blocking)
while let Some(ev) = event_rx.recv().await {
    // ev: EventRecord, finalized, identical order on every peer
}
c.deactivate()?;                          // -> Inactive (stops the engine thread)
c.shutdown()?;                            // -> Finalized (not idempotent: a second call errors)

Key types, all defined in the crate:

TypeWhat it is
Controllerthe lifecycle orchestrator. Owns the engine thread. configure / activate / deactivate / cleanup / shutdown / submit / status
Configbind_address (literal IP:port, no DNS), key: KeySecret, peers: Vec<PeerConfig>, joining_running_session, bridge, options
PeerConfigone remote peer: address plus KeyPublic. Parses the "<base58_pubkey>@<ip:port>" spec form
BridgeConfigchannel bounds: tx_channel_capacity 1024, event_channel_capacity 4096 by default
VertexOptionsmirrors 15 of the engine's 19 tunables (missing: max_resident_bytes, storage_path, strict_replay_verify, wait_for_state_report). Defaults match the engine's: heartbeat_us 500000, target_ack_latency_ms 400, transaction_channel_size 32, dynamic epoch sizing and hole punching on
EventRecorda finalized event, fully copied out of FFI memory: consensus_at, created_at, hash: [u8; 32], creator_pub_der, whitened_signature, transactions: Vec<TransactionRecord>
Status / StatusSnapshotlock-free counters: running, peer count, tx_submitted_total, tx_rejected_total, events_published_total, last error
The controller always inserts yourself into the peer set, so Config.peers lists only the other nodes. Total session size is peers.len() + 1, and the BFT sizing rule from the first tutorial (n ≥ 3f + 1) applies to that total.

Step 1Workspace and build plumbing

vertex_core pins tashi-vertex to an exact version from crates.io, so tessera is the only checkout you need beside your own crate:

shell
workspace/
├── tessera/            # vertex_core lives at tessera/vertex_core
└── my-fleet/           # your new crate
toml — my-fleet/Cargo.toml
[package]
name = "my-fleet"
edition = "2021"

[dependencies]
vertex_core = { path = "../tessera/vertex_core" }
tashi-vertex = "=0.14.0"   # for KeySecret / KeyPublic
tokio = { version = "1", features = ["rt-multi-thread", "macros", "time"] }
Match vertex_core's pinned version exactly. The engine handles are FFI types, so if cargo resolves two different tashi-vertex versions you get two incompatible copies of KeySecret, Engine and friends, and the mismatch surfaces as a type error rather than anything that hints at the real cause. The pin lives in tessera/vertex_core/Cargo.toml.

Two build facts to know before your first cargo build:

  • The C engine. tashi-vertex builds against libtashi-vertex (the actual consensus engine, a C library). Its build downloads the release archive pinned inside that crate version. To build against a local checkout instead, set TASHI_VERTEX_LOCAL_BUILD=1 and point TASHI_VERTEX_LOCAL_DIR at it — the flag gates the local build, the path just tells it where to look, and setting the path alone leaves the flag off and the release download still happens. Tessera's Docker harness sets both automatically whenever TASHI_VERTEX_LOCAL_DIR is present (docker/entrypoint.sh).
  • The rpath problem. The bindings' build script adds an rpath only to its own binaries. Downstream binaries link libtashi-vertex.so/.dylib but cannot find it at runtime. vertex_core ships a build.rs that locates the library under the shared target directory and bakes an absolute rpath plus $ORIGIN-style fallbacks. Copy that build.rs into your crate, or export LD_LIBRARY_PATH the way tessera's docker/entrypoint.sh does (export_tv_libpath).

Step 2Keys and configuration in code

At this layer you do not need JSON fixtures or shell scripts. Identities are two calls, and the base58 forms round-trip through Display/FromStr when you want to persist them:

rust
use tashi_vertex::KeySecret;
use vertex_core::{Config, PeerConfig, BridgeConfig, VertexOptions};

let key = KeySecret::generate();          // fresh identity
let b58 = key.to_string();                // persist this (file, vault, ...)
let key = Config::secret_from_base58(&b58)?;   // ...and load it back

// peers accept the same "<pubkey>@<ip:port>" spec the ROS parameter uses
let peers = Config::peers_from_specs([
    "6Yx...@10.0.0.2:47611",
    "9Kp...@10.0.0.3:47611",
])?;

let config = Config {
    bind_address: "10.0.0.1:47611".into(),  // literal IP, no DNS
    key,
    peers,                                   // the OTHERS; self is auto-inserted
    joining_running_session: false,
    bridge: BridgeConfig::default(),         // tx 1024 / event 4096
    options: VertexOptions {
        heartbeat_us: 50_000,                // small sessions form events faster
        ..VertexOptions::default()
    },
};
For small test meshes, drop heartbeat_us from the 500 ms default to 50 ms, exactly what tessera's own tests and the simulation do. Events form quickly and teardown observes its stop flag sooner (the receive loop wakes at most one heartbeat apart).

Step 3A headless three-node fleet, no ROS anywhere

This is the canonical lower-level usage and it is lifted from a test tessera runs on every push (vertex_core/tests/multi_node.rs): three real engines in one process, gossiping over localhost UDP, asserting the totally-ordered guarantee. Strip the asserts and this skeleton is your application main:

rust — three in-process peers
use tashi_vertex::KeySecret;
use vertex_core::{Config, Controller, PeerConfig};

// --- identities: three keypairs, three localhost ports ---
let nodes: Vec<(KeySecret, String)> = (0..3)
    .map(|i| (KeySecret::generate(), format!("127.0.0.1:{}", 47411 + i)))
    .collect();

// --- one Controller per node, each listing the OTHER two as peers ---
let mut controllers = Vec::new();
let mut receivers = Vec::new();
for i in 0..nodes.len() {
    let peers = nodes.iter().enumerate()
        .filter(|(j, _)| *j != i)
        .map(|(_, (k, addr))| PeerConfig { address: addr.clone(), public: k.public() })
        .collect();
    // KeySecret is not Clone; round-trip DER so each Controller owns a copy
    let key = KeySecret::from_der(&nodes[i].0.to_der_vec()?)?;
    let mut c = Controller::new();
    c.configure(Config { bind_address: nodes[i].1.clone(), key, peers,
                         joining_running_session: false,
                         bridge: Default::default(), options: options() })?;
    let (event_rx, _sync_rx) = c.activate()?;   // engine thread starts here
    controllers.push(c);
    receivers.push(event_rx);
}

// --- submit from any node; observe the SAME order on every node ---
controllers[0].submit(b"hello from node 0".to_vec());
controllers[2].submit(b"and node 2".to_vec());

// each receiver yields EventRecords; the streams are byte-identical:
//   assert_eq!(&streams[n][idx], &streams[0][idx])   for every idx, n

Three details in that skeleton repay attention:

  • activate() fails synchronously if the bind or the engine start fails. The engine thread reports startup before entering its receive loop, so you never end up half-active.
  • submit() never blocks. A full inbound channel counts the payload into tx_rejected_total and drops it: backpressure is visible, not silent.
  • The receivers are Tokio mpsc receivers. In async code use recv().await. In a plain thread use blocking_recv(), which is exactly what the ROS adapter's pump threads do.

Step 4The concurrency contract you inherit for free

The reason to embed Controller rather than calling the bindings directly is that the engine's FFI surface has sharp edges, and vertex_core already wraps every one of them. If you bypass it, you must replicate all of this:

  • Engine handles are !Send. Context, Engine, Socket, Peers, and Options wrap raw pointers and can never cross threads or be tokio::spawned. The controller therefore runs the engine on one dedicated OS thread with a current-thread Tokio runtime, and only Send data (payload bytes, EventRecords, DER-encoded keys) crosses the channel boundary.
  • recv_message() is not cancellation-safe. Its future registers a pointer with the C library on first poll. Racing it inside a tokio::select! drops the losing future and the C callback later writes into freed memory. vertex_core runs two cooperative tasks instead: a receive loop that is never cancelled mid-flight (it exits between messages via a stop flag) and a send loop that only selects over cancellation-safe futures.
  • There is no Engine::stop. Teardown is dropping the engine and then its Context, and the Context must outlive the Engine. deactivate() waits up to five seconds for the engine thread to wind down and then detaches it rather than hanging forever (an engine that lost quorum can stall in recv_message).
  • Transaction is move-only. Submission is allocate, copy, send, and the type system forbids double-send and double-free. This is also why tessera's Miri CI job covers the pure modules and leaves the FFI to the move-only guarantee.
  • Events are copied out eagerly. EventRecord::from_event clones every borrowed slice out of FFI-owned memory before the event is dropped, so nothing downstream ever touches engine memory.
If your plan was "just call tashi-vertex directly from my async runtime", stop and reread the second bullet. The safe embedding is genuinely nontrivial, and it is exactly the part vertex_core has already solved and tested. Target the bindings directly only if you cannot take a Tokio dependency at all.

Step 5Writing your own adapter (the vertex_ros2 pattern)

vertex_ros2 is a worked example of wrapping Controller for a middleware, and it is thin by design: about three files. To adapt tessera to anything else (Zenoh, MQTT, gRPC, DDS without ROS), reproduce its five moves with your transport:

  1. Hold one Controller behind a mutex in your service process.
  2. Expose the five lifecycle verbs (configure / activate / deactivate / cleanup / shutdown) as an RPC, and publish the resulting state (unconfigured / inactive / active / finalized) somewhere late joiners can read it. The ROS adapter uses a service plus a latched topic.
  3. Ingress: your transport's receive callback calls controller.submit(payload). Nothing else. It is non-blocking and safe from any thread.
  4. Egress: when activate() hands you the receivers, spawn pump threads and forward in order. Order preservation IS the product, so this loop must be the only consumer:
rust — the pump, verbatim pattern from the ROS adapter
std::thread::Builder::new().name("event-pump".into()).spawn(move || {
    while let Some(rec) = event_rx.blocking_recv() {
        let _ = my_transport.publish(convert(rec));   // your wire format
    }
})?;
  1. Diagnostics: expose controller.status() snapshots (submitted, rejected, published, last error) on whatever health channel your stack has. The rejected counter is your only backpressure signal, so surface it.

The contract your adapter must preserve, because everything above it depends on these:

  • events go out in exactly the order the receiver yields them, one consumer, no reordering, no dropping
  • nothing is published while the node is not Active
  • payloads are opaque: no inspection, no rewriting, no compression tricks

Step 6Testing at this layer

Plain cargo test in vertex_core runs the whole suite against the real engine, no ROS, no simulator. The four integration tests are also the templates for testing your embedding:

TestWhat it proves, and what to copy
single_node.rsdelivery integrity on a solo session: everything submitted comes back finalized
multi_node.rsthe real guarantee: three peers, byte-identical totally-ordered event streams. Copy its collect_until drain helper and its stream-prefix comparison
lifecycle_behavior.rstransition guards: what is legal from which state, teardown from every state
tx_saturation.rsbackpressure: flooding submit() raises tx_rejected_total instead of blocking or leaking

For your own project, the one test I would not skip is the multi-node stream comparison. It catches everything from misconfigured peer sets to an adapter that reorders events:

rust — the assertion that matters
let min_len = streams.iter().map(|s| s.len()).min().unwrap();
assert!(min_len > 0, "no events collected");
for idx in 0..min_len {
    for s in &streams[1..] {
        assert_eq!(&s[idx], &streams[0][idx], "consensus order divergence");
    }
}

Pitfalls at this layer

  • DNS in bind_address. Addresses are literal IP:port, both for binding and in peer specs. Resolve names yourself before building the config.
  • Forgetting you are a peer too. The controller inserts you into the peer set automatically. If you also list yourself in Config.peers, you have a duplicate.
  • KeySecret is not Clone. To hand the same identity to two places, round-trip it through DER (to_der_vec / from_der), as the multi-node test does.
  • Slow event consumers. The outbound event channel is bounded (4096 by default). A consumer that stalls eventually blocks the engine task. Keep the pump loop trivial and hand off heavy work to another thread.
  • Expecting to rejoin after a restart. A restarted process is a new participant. joining_running_session exists for rejoining an in-flight session but is an upstream feature with limits. Design recovery at the protocol level (epochs and resets, as in the first tutorial).
  • Timestamp units. The upstream engine now documents its timestamps explicitly as nanoseconds since the Unix epoch, part of the API contract. Tessera still centralizes the interpretation in one function (convert::nanos_to_time) rather than inlining it everywhere, so if that contract ever changes it stays a one-line fix — route any time handling of your own through the same single point.
  • Sync points are placeholders. SyncPointRecord.payload is empty until upstream exposes accessors. Do not build features on it yet.
