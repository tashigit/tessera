Adding Vertex consensus to your ROS 2 project with vertex_fleet

This is the fastest route from an existing ROS 2 fleet to leaderless, BFT-consensus coordination: two base classes from the vertex_fleet library, one launch pattern, and a handful of rules the library enforces for you. I build a complete, realistic example along the way: robots allocating charging docks among themselves with no server and no leader.

The series. 1 · Concepts and protocol design (the mental model)  →  2 · The fleet API (you are here)  →  3 · Crate-level internals (non-ROS embeddings and adapters). This volume stands alone; read Volume 1 when you design a protocol beyond the patterns shown here.

You need: a ROS 2 Jazzy workspace with the tessera packages built (section 1), and a fleet problem where machines must agree.

Where this fits

The tessera integration exposes Vertex consensus to ROS 2 at three levels. This tutorial covers the top one, which is where most projects should start:

LevelYou writeCovered in
vertex_fleet (this tutorial)a state class and an agent class; the library owns the consensus plumbinghere
raw topic contractyour own fold and lifecycle handling against /vertex/tx and /vertex/eventVolume 1 (concepts and protocol design)
Rust crate (vertex_core)an embedding with no ROS at all, or an adapter for another middlewareVolume 3 (crate-level internals)

The one-paragraph mental model, in case you land here first: every robot runs a vertex_node, the engines gossip over UDP, and every robot receives the same totally-ordered stream of finalized records. Nothing else is shared. Each robot folds that stream through the same pure function, so each robot derives the same fleet state, and coordination follows with no leader, no server, and tolerance of f crashed or malicious robots in a fleet of 3f + 1.

The two base classes

An application on vertex_fleet is one subclass of each:

You implementOnContract
wipe()ReplicatedStateclear every piece of derived state (called at construction and on a consensus reset)
apply_record(rec)ReplicatedStatefold ONE record into state. Pure and idempotent: no I/O, no clocks, no randomness, duplicates change nothing
tick()VertexAgentperiodic hook, runs only while the engine is Active. Read state, read sensors, call propose(...)
on_state_changed()VertexAgentcalled after each consensus event folds. React to the new state (drive, navigate, actuate)
on_event(msg) (optional)VertexAgentthe raw finalized event (hash, timestamps, transactions) for logging and telemetry

And what the library gives you in return:

  • propose(record) submits a record stamped with the current epoch. It has no local effect: state changes only if and when the record returns finalized, identically on every robot
  • propose_reset(epoch) restarts the whole fleet's state at a fresh epoch through consensus (first reset in the order wins)
  • epoch gating: records from earlier epochs are ignored automatically
  • lifecycle bring-up: the agent drives its own vertex_node to Active and retries until it succeeds; engine_running tells you where it stands
  • the structural guarantee that makes everything work: your state has exactly one mutation path, the consensus event callback. Sensors and timers can read it and propose, never write it

Step 2Model the shared state

The worked example: a warehouse fleet with a few charging docks. Robots decide among themselves who gets which dock. No dock server, no fleet manager, and the allocation survives any single robot crashing mid-negotiation.

Design the records first. Two verbs are enough, and the noun names say what agreement is about:

jsonc — the protocol
{ "op": "claim",   "robot": "r0", "dock": "dock_a", "epoch": 0 }
{ "op": "release", "robot": "r0", "dock": "dock_a", "epoch": 0 }

Then the fold. This is the most important twenty lines of your integration, and the library keeps them honest: epoch gating and reset handling are inherited, so the subclass folds only its own ops. Keep it pure, keep it idempotent, and resolve every conflict by log order:

python — my_fleet/dock_state.py (pure, no ROS imports)
from vertex_fleet import ReplicatedState

DOCKS = ["dock_a", "dock_b"]

class DockState(ReplicatedState):
    """Who holds which charging dock. Same log in, same allocation out,
    on every robot."""

    def wipe(self):
        self.occupied = {}                          # dock -> robot

    def apply_record(self, rec):
        op, robot, dock = rec.get("op"), rec.get("robot"), rec.get("dock")
        if op == "claim":
            # first claim in the finalized order wins; a robot holds at
            # most one dock; duplicates and losers are no-ops
            if (dock in DOCKS and dock not in self.occupied
                    and robot not in self.occupied.values()):
                self.occupied[dock] = robot
        elif op == "release":
            # only the holder can release; anything else is a no-op
            if self.occupied.get(dock) == robot:
                del self.occupied[dock]

    def dock_of(self, robot):
        for dock, holder in self.occupied.items():
            if holder == robot:
                return dock
        return None

Step 3Write the agent

The agent connects three things: the shared state (folded for you), your robot's own sensors (battery, here), and your actuators (your navigation stack). Step through how it assembles, then take the complete file below.

Agent assembly, one decision at a time

Each step adds the highlighted lines and explains why they exist.

  

    
    
    
  





The complete file, ready to copy:


python — my_fleet/dock_agent.py
from std_msgs.msg import Float32, String

from vertex_fleet import VertexAgent, spin_agent
from my_fleet.dock_state import DOCKS, DockState


class DockAgent(VertexAgent):
    def __init__(self):
        super().__init__("dock_agent", DockState())
        self.declare_parameter("robot_name", "r0")
        self.me = self.get_parameter("robot_name").value
        self.battery = 1.0
        self.create_subscription(Float32, "battery_level",
                                 self._on_battery, 10)
        self._goal_pub = self.create_publisher(String, "dock_goal", 10)
        self._last_goal = None

    def _on_battery(self, msg):
        self.battery = float(msg.data)      # local sensor: mine alone

    def tick(self):
        # intent from LOCAL facts + SHARED state -> proposals, nothing else.
        # Never assume a proposal succeeded: keep proposing until the
        # folded state shows it (duplicates fold as no-ops).
        mine = self.state.dock_of(self.me)
        if self.battery < 0.20 and mine is None:
            free = [d for d in DOCKS if d not in self.state.occupied]
            if free:
                self.propose({"op": "claim",
                              "robot": self.me, "dock": free[0]})
        elif self.battery > 0.95 and mine is not None:
            self.propose({"op": "release",
                          "robot": self.me, "dock": mine})

    def on_state_changed(self):
        # the ONLY place behavior follows from: the folded shared state.
        # Hand the goal to your own navigation (Nav2 action, etc.).
        goal = self.state.dock_of(self.me)
        if goal != self._last_goal:
            self._last_goal = goal
            self._goal_pub.publish(String(data=goal or "none"))


def main():
    spin_agent(DockAgent)



If your state needs ROS parameters to construct (dock list from a param, for example), pass state=None to super().__init__ and assign self.state right after: no callback runs before spinning. The route-exploration simulation in the repository does exactly this.

Step 5Launch the fleet


Per robot: one vertex_node with the contract topics remapped into the robot's namespace, plus your agent in the same namespace. The relative topics (vertex/tx, vertex/event, battery_level, dock_goal) all resolve under it:


python — my_fleet/launch/fleet.launch.py
import json
from launch import LaunchDescription
from launch_ros.actions import Node

peers = json.load(open("peers.json"))

def generate_launch_description():
    actions = []
    for i, me in enumerate(peers):
        ns = f"/r{i}"
        others = [p for j, p in enumerate(peers) if j != i]
        actions.append(Node(
            package="vertex_ros2", executable="vertex_node", name=f"vertex{i}",
            remappings=[(f"/vertex/{t}", f"{ns}/vertex/{t}")
                        for t in ("tx", "event", "sync_point",
                                  "status", "transition")]
                      + [("/vertex/lifecycle/state",
                          f"{ns}/vertex/lifecycle/state")],
            parameters=[{
                "vertex.bind_address": me["addr"],
                "vertex.secret_key_base58": me["secret"],
                "vertex.peers": [f"{p['public']}@{p['addr']}" for p in others],
                "options.heartbeat_us": 50000,
            }],
        ))
        actions.append(Node(
            package="my_fleet", executable="dock_agent",
            name="dock_agent", namespace=ns,
            parameters=[{"robot_name": f"r{i}"}],
        ))
    return LaunchDescription(actions)



The agents bring their engines to Active on their own. Watch it work by faking a low battery on one robot:


shell
ros2 topic pub --once /r0/battery_level std_msgs/msg/Float32 "{data: 0.1}"
ros2 topic echo /r0/dock_goal      # -> "dock_a" once the claim finalizes
ros2 topic echo /r1/dock_goal      # r1 sees r0's claim too: shared state



Size the fleet for the faults you must survive: the quorum rule is n ≥ 3f + 1, so three robots tolerate none and four robots is the smallest fleet that keeps working with one crashed.



Step 6Test it


Two test shapes cover almost everything, and both have ready templates in the repository.


Unit: determinism of your fold. Pure Python, no ROS, runs anywhere. Feed the same log to several instances and assert they agree, then feed the hostile cases: duplicates, stale epochs, conflicting claims:


python — test/test_dock_state.py
def test_conflicting_claims_one_winner_everywhere():
    log = [{"op": "claim", "robot": "r0", "dock": "dock_a", "epoch": 0},
           {"op": "claim", "robot": "r1", "dock": "dock_a", "epoch": 0}]
    fleet = [DockState() for _ in range(4)]
    for s in fleet:
        for rec in log:
            s.apply(rec)
    assert all(s.occupied == {"dock_a": "r0"} for s in fleet)



Integration: real consensus, launch_testing. Start real vertex_node peers and your agents, drive the scenario, and assert two things: the outcome (the allocation you expect) and the transport guarantee underneath (byte-identical /vertex/event streams across robots). Copy vertex_fleet/test/ledger_demo.launch_test.py and swap in your topics; it is exactly this shape, kept green in CI.



The rules that keep fleets convergent


The library enforces the structural ones. The rest are yours to keep, and each has drawn blood in the flagship simulation, so treat the war stories as free experience:


    
  
  1. The fold is sacred. Pure, idempotent, no clocks, no randomness, no I/O. One stray random() in apply_record and your robots silently diverge. Randomness belongs on the proposal side (which dock to try), never in the fold.
    2. 
  
  2. Propose, then wait. A proposal takes effect only when it returns finalized. Act on self.state, never on what you just proposed. Re-proposing while waiting is free because your fold is idempotent.
    3. 
  
  3. First in the log wins. Never negotiate, never retry-with-backoff-and-priority. Conflicts resolve by finalized order, identically everywhere, at zero protocol cost.
    4. 
  
  4. Gate physical evidence to what it is evidence of. Two real bugs, same disease: an arrival check that tested only "past the goal line" credited a robot's assigned route when the world shoved it down a different one, and a latched barrier flag from an old route got charged to a robot's new target within one tick, poisoning an open route for the whole fleet. Sensor facts are only valid for the target they were sensed against, and only if they postdate the assignment.
    5. 
  
  5. Reflexes stay local. Collision avoidance, safety stops, and motion control cannot wait for a consensus round trip. Keep them in the robot, deterministic, and out of the log.
    6. 
  
  6. Design recovery as epochs. A restarted process is a new participant and does not relearn missed decisions. Do not build resume-where-I-left-off; build propose_reset(epoch + 1) and make starting over cheap.
    7. 
  
  7. Lease what a robot can hold. A crashed robot cannot release its dock. Let any robot propose a timeout for a holding that has shown no progress past a lease window; make the release a checked no-op if the holder already moved on. The simulation's fault-injection test is the worked example.
